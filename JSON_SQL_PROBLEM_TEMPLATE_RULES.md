# JSON SQL Problem Document Template — Rules & Regulations

**Purpose:** defines the strict, field-by-field contract for authoring a **`type: "sql"`** question as a single JSON document. Every field below maps 1:1 onto the SQL publish payload accepted by the backend and onto the `sqlMeta` sub-document of the `Question` model in MongoDB.

This is the SQL counterpart of `JSON_PROBLEM_TEMPLATE_RULES.md`. Rules that are specific to programming questions (boilerplate with `T`, `languages`, `scoringTiers`, `testCases` with stdin/stdout) **do not apply here**.

---

## 0. How the JSON is consumed

| Step | Action | Endpoint |
|---|---|---|
| 1 | **Generate Outputs** — runs `solutionSql` against every `seedSql` in a real MySQL container and returns the generated `expected` rows. Writes nothing. | `POST /api/cohorts/:cohortId/modules/:moduleId/sql-questions/generate-outputs` |
| 2 | **Validate Testcases** — re-executes and diffs the generated rows against the `expected` you supplied in the JSON. Optional but recommended. | `POST /api/cohorts/:cohortId/modules/:moduleId/sql-questions/validate` |
| 3 | **Submit / Publish** — writes `schema.sql`, `solution.sql`, and per-testcase `seed.sql` + `expected.json` to S3, then saves the `Question` document. | `POST /api/cohorts/:cohortId/modules/:moduleId/sql-questions` |

Hard rules:

- **One JSON file = one SQL question.** The bulk upload endpoint explicitly rejects `type: "sql"`.
- **Testcase data never lands in MongoDB.** Mongo stores only S3 object keys, the engine question id, the version, and display-safe assets. `expected.json` is regenerated by the engine at publish time, so a wrong `expected` in your JSON can never corrupt grading — it only fails validation.
- **Publishing is versioned and immutable.** Republishing the same `judgeQuestionId` + `judgeVersion` requires `"overwrite": true`; otherwise bump `judgeVersion`.
- Fields not listed in this document are **ignored** by the SQL payload parser. In particular there is no `questionBank`, no `languages`, no `scoringTiers`, no `timeLimit`, and no `memoryLimit` for SQL questions.

---

## I. Top-level fields

### 1. `title` — required
- Short, clear, human readable. This is also the default source of `judgeQuestionId` (slugified) and `slug`.
- Example: `"Average Salary By Department"`.

### 2. `description` — required
- HTML string. Full rules in **Section II** below.

### 3. `type` — required
- Exactly `"sql"`.

### 4. `difficultyLevel` — required
- One of `easy`, `medium`, `hard`. Note the field name is `difficultyLevel`, **not** `difficulty`.

### 5. `marks` — required
- SQL grading is **all-or-nothing**: full marks only when every visible **and** hidden testcase passes. There are no scoring tiers, so a single number is the whole score.
- Convention:
  - `easy` = **30**
  - `medium` = **60**
  - `hard` = **100**

### 6. `judgeQuestionId` — optional
- The immutable S3 identity of the question inside SQLJudge. Defaults to a slug of `title`.
- Must match `[A-Za-z0-9][A-Za-z0-9._-]{0,64}`.
- Once published, treat it as permanent. Changing it creates a different question.

### 7. `judgeVersion` — optional
- Positive integer, defaults to `1`. Also accepted as `version` or `"v2"`.
- Bump it whenever the schema, the solution, or any seed changes in a way that alters expected output.

### 8. `schemaSql` — required
- The complete DDL that creates every table the query may read. Also accepted as `schema`.
- Rules:
  - One statement per table, each terminated with `;`.
  - `CREATE TABLE` only. No `INSERT` here — rows belong to `seedSql`.
  - Prefer explicit column types and a primary key on every table.
  - Use `CREATE TABLE IF NOT EXISTS` for safety; the container is thrown away per run either way.
  - MySQL 8.4 dialect.

### 9. `solutionSql` — required
- The reference query. Also accepted as `solution`.
- Rules:
  - A **single** `SELECT` statement, terminated with `;`.
  - Must be deterministic: if the problem does not define an order, the engine compares row sets, but any query whose output depends on an arbitrary tie-break must pin it with `ORDER BY`.
  - Column aliases in the reference query define the **expected column names** students must reproduce. Alias every computed column.
  - Never stored in the API response and never sent to students (`select: false` in Mongo).

### 10. `boilerplateSql` — required
- The starting content of the student's editor. Defaults to:
  ```sql
  -- Write your query below.
  SELECT
  ```
- Keep it minimal: a comment plus a stub. Never include a partial solution.

### 11. `testcases` — required
- Array, 1 to **50** entries. Full rules in **Section III**.

### 12. `constraints` — optional
- Array of plain strings (or a newline-separated string). Stored alongside the question in S3 for reference.
- This is **not** a substitute for the `<h3>Constraints:</h3>` block in the description; write both.

### 13. `hints` — required
- 1 to 3 short strings. Nudge toward the SQL feature needed (`GROUP BY`, window function, self join) without writing the query.

### 14. `tags` — required
- Array of sub-topics: `joins`, `group-by`, `aggregation`, `window-functions`, `subquery`, `cte`, `date-functions`.

### 15. `companies` — required
- Array of company names, from trusted sources only.

### 16. `editorial` — required
- HTML string explaining the approach after solving. Same HTML conventions as the description. Include the reference query in a `<pre><code>` block.

### 17. `overwrite` — optional
- `true` only when deliberately republishing an existing `judgeQuestionId` + `judgeVersion`.

## II. `description` — HTML rules

Follow this exact sequence. Every rule from the programming HTML template still applies: no emojis, no inline styles except on `<img>` and `<table>`, only the pre-defined classes `example`, `label`, `value`, `note`.

1. **Question Description** (required)
2. **Table Schema** (required — replaces "Input Format")
3. **Output Format** (required)
4. **Examples** (required — 1 to 3, one per visible testcase)
5. **Constraints / Rules** (required)
6. **Note** (required — must state the tables already exist)

### Section 1 — Question Description

- State the business question in plain language. Wrap every table name, column name, alias, and SQL keyword in `<code>`.
- Do not reveal the approach (no "use a self join", no "use `ROW_NUMBER()`").

```html
<p>The table <code>employees</code> stores one row per employee, including the department they belong to and their monthly salary.</p>

<p>Write a query that reports the <strong>average salary of each department</strong>, so the report can be published department by department.</p>
```

### Section 2 — Table Schema (required)

- Render every table as an HTML table of column name, type, and meaning. This is what replaces "Input Format" for SQL.
- The columns listed here must match `schemaSql` exactly.

```html
<h3>Table: employees</h3>
<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse; width: 100%; margin: 10px 0;">
    <thead>
        <tr>
            <th>Column</th>
            <th>Type</th>
            <th>Description</th>
        </tr>
    </thead>
    <tbody>
        <tr>
            <td><code>id</code></td>
            <td><code>INT</code></td>
            <td>Primary key.</td>
        </tr>
        <tr>
            <td><code>name</code></td>
            <td><code>VARCHAR(100)</code></td>
            <td>Employee name.</td>
        </tr>
        <tr>
            <td><code>department</code></td>
            <td><code>VARCHAR(50)</code></td>
            <td>Department the employee belongs to.</td>
        </tr>
        <tr>
            <td><code>salary</code></td>
            <td><code>INT</code></td>
            <td>Monthly salary in rupees.</td>
        </tr>
    </tbody>
</table>
<br>
```

### Section 3 — Output Format (required)

- List the result columns **in order**, with the exact alias each one must carry. Column names are compared, so this section is a contract.

```html
<h3>Output Format</h3>
<ul>
    <li>One row per department present in <code>employees</code>.</li>
    <li>Column <code>department</code> — the department name.</li>
    <li>Column <code>avg_salary</code> — the average salary of that department.</li>
    <li>Rows must be ordered by <code>department</code> in ascending order.</li>
</ul>
```

### Section 4 — Examples (required)

- One example per **visible** testcase, in the same order as the `testcases` array, and the numbers must match that testcase's `seedSql` exactly.
- Each example needs three parts: **Input** (the seeded rows), **Expected Output** (the result set), and **Explanation**.
- Show input and expected output as HTML tables — a SQL result set is tabular, so `class="example"` label/value pairs are not used here.

```html
<h3>Examples:</h3>

<p><strong>Example 1:</strong></p>
<p><strong>Input:</strong> <code>employees</code></p>
<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse; width: 100%; margin: 10px 0;">
    <thead>
        <tr><th>id</th><th>name</th><th>department</th><th>salary</th></tr>
    </thead>
    <tbody>
        <tr><td>1</td><td>Asha</td><td>HR</td><td>50000</td></tr>
        <tr><td>2</td><td>Ravi</td><td>IT</td><td>60000</td></tr>
        <tr><td>3</td><td>Neha</td><td>IT</td><td>70000</td></tr>
    </tbody>
</table>

<p><strong>Expected Output:</strong></p>
<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse; width: 100%; margin: 10px 0;">
    <thead>
        <tr><th>department</th><th>avg_salary</th></tr>
    </thead>
    <tbody>
        <tr><td>HR</td><td>50000</td></tr>
        <tr><td>IT</td><td>65000</td></tr>
    </tbody>
</table>

<p><strong>Explanation:</strong></p>
<p><code>HR</code> has a single employee earning <code>50000</code>, so its average is <code>50000</code>. <code>IT</code> has two employees earning <code>60000</code> and <code>70000</code>, so its average is <code>(60000 + 70000) / 2 = 65000</code>. Rows are returned in ascending order of <code>department</code>, which places <code>HR</code> before <code>IT</code>.</p>

<br>
```

Explanation rules:
- Show the arithmetic or the filtering logic that produces each row. "Because of the group by" is not an explanation.
- Explain why rows are **excluded** when the example covers a filter, a `JOIN` that drops rows, or a `NULL`.
- Minimum one full sentence per output row for small examples.

### Section 5 — Constraints / Rules (required)

SQL correctness hinges on formatting details that a programming question never has to state. Cover every one that applies:

```html
<h3>Constraints:</h3>
<ul>
    <li><code>1 &le; number of rows in employees &le; 10<sup>4</sup></code></li>
    <li><code>0 &le; salary &le; 10<sup>7</sup></code></li>
    <li><code>department</code> is never <code>NULL</code>.</li>
</ul>

<h3>Rules:</h3>
<ul>
    <li><strong>Column names must match exactly:</strong> <code>department</code>, <code>avg_salary</code>.</li>
    <li><strong>Column order must match</strong> the Output Format section.</li>
    <li><strong>Ordering:</strong> results must be sorted by <code>department</code> ascending. Add an explicit <code>ORDER BY</code>; do not rely on insertion order.</li>
    <li><strong>Rounding:</strong> round <code>avg_salary</code> to <strong>2 decimal places</strong>.</li>
    <li><strong>Ties:</strong> when two departments share the same average, order them by <code>department</code> ascending.</li>
    <li><strong>Empty result:</strong> return zero rows rather than a row of <code>NULL</code> values.</li>
    <li>Use a single <code>SELECT</code> statement. Do not create, alter, or drop any object.</li>
</ul>
```

Checklist of rules to consider for every SQL question:

| Concern | State it when |
|---|---|
| Exact column names / aliases | Always |
| Column order | Always |
| Row ordering, and the tie-break | Always — either an explicit `ORDER BY` or "any order" |
| Rounding / decimal places | Any `AVG`, `SUM` of decimals, division, or percentage |
| `NULL` handling | Any nullable column, `LEFT JOIN`, or aggregate over nullables |
| Case sensitivity | Comparing or grouping text |
| Duplicates | `DISTINCT` expected, or duplicates intentionally kept |
| Empty result | A filter can eliminate every row |
| Date formats | Any date output, e.g. `YYYY-MM-DD` |
| Limits | Top-N questions |

Numeric comparison is canonical: `65000`, `65000.00`, and `"65000.00"` compare equal. Rounding still matters, because `65000.33` and `65000.3` do not.

### Section 6 — Note (required)

The Note block **must** state that the tables already exist, so nobody wastes an attempt writing DDL.

```html
<div class="note">
    <p><strong>Note:</strong></p>
    <ul>
        <li>All tables listed above are <strong>already created and populated</strong> before your query runs. Do <strong>not</strong> write <code>CREATE TABLE</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>, or <code>DROP</code> statements.</li>
        <li>Submit a <strong>single <code>SELECT</code> statement</strong> ending with a semicolon. Only the result of that statement is compared.</li>
        <li>The query runs on <strong>MySQL 8.4</strong>.</li>
        <li>Your result is compared on <strong>column names, column order, and row values</strong>. Numeric values compare equal regardless of trailing zeros, so <code>65000</code> matches <code>65000.00</code>.</li>
        <li><strong>Run</strong> checks the sample testcases only. <strong>Submit</strong> grades against additional hidden testcases, and full marks require every testcase to pass.</li>
        <li>If the question fails to explain correctly then report your problem to admin.</li>
    </ul>
</div>
```

## III. `testcases` — rules

Each entry is one throwaway database: the engine creates the schema, applies that testcase's `seedSql`, runs the query, and compares against `expected.json`.

### Field rules

| Field | Required | Rules |
|---|---|---|
| `id` | optional | Matches `[A-Za-z0-9][A-Za-z0-9._-]{0,64}`, unique within the question. Defaults to `tc-01`, `tc-02`, … Use that convention; the id becomes part of the S3 key. |
| `seedSql` | **required** | The `INSERT` statements for this testcase only. |
| `visible` | optional | `true` shows the testcase to students. Defaults to `true` unless `hidden: true` is given. **At least one testcase must be visible.** |
| `expected` | optional | `{ "columns": [...], "rows": [[...]] }`. Used only by Validate. Publishing regenerates it from `solutionSql`, so it is a self-check, never the source of truth. |

### Content rules

- **`seedSql` contains data only.** No `CREATE TABLE` — the schema comes from `schemaSql` and is applied first. Every statement ends with `;`.
- **Each testcase is independent.** No testcase may depend on rows seeded by another.
- **Visible testcases stay small:** 3 to 6 rows per table, so the tables render readably in the results panel and match the examples in the description exactly.
- **Hidden testcases carry the coverage.** Aim for 4 to 8 total, with at least 2 hidden. Each must probe a distinct property:
  - empty table, or a filter that matches nothing
  - a single row
  - ties on the ordering key
  - `NULL` in every nullable column
  - values that force the rounding rule to bite (an average like `65000.333…`)
  - duplicates, when the question is about `DISTINCT` or `GROUP BY`
  - the boundary of the stated constraints
  - rows deliberately dropped by the intended `JOIN`, plus a case where a `LEFT JOIN` must keep them
- Never seed data whose expected output you cannot justify by hand. Run **Generate Outputs** and read the result before publishing.

### Required assets per testcase

Publishing produces exactly this layout in S3, which is why every testcase must carry its own seed:

```
private/questions/<judgeQuestionId>/v<judgeVersion>/
    schema.sql                        <- from schemaSql        (one per question)
    solution.sql                      <- from solutionSql      (one per question)
    question-config.json
    testcases/<id>/seed.sql           <- from testcases[].seedSql   (one per testcase)
    testcases/<id>/expected.json      <- generated from solution.sql (one per testcase)
public/questions/<judgeQuestionId>/v<judgeVersion>/
    question.json                     <- student-facing metadata + visible testcases
```

So the JSON you author **must** supply, in one document:
- `schemaSql` — the single `schema.sql` shared by all testcases,
- `solutionSql` — the single `solution.sql` used to generate every `expected.json`,
- `testcases[i].seedSql` — a distinct `seed.sql` for **every** testcase, visible and hidden alike.

A question is not publishable if any testcase is missing its `seedSql`.

## V. Validation checklist

Payload:
- [ ] `type` is `"sql"`, `difficultyLevel` is `easy` / `medium` / `hard`, `marks` follows the 30 / 60 / 100 convention
- [ ] `judgeQuestionId` matches the id pattern and is not already published at this `judgeVersion`
- [ ] `schemaSql` has `CREATE TABLE` only, `solutionSql` is one `SELECT`, both end with `;`
- [ ] Every computed column in `solutionSql` is aliased, and the aliases match the Output Format section
- [ ] `boilerplateSql` reveals nothing

Testcases:
- [ ] Every testcase has a unique `id` and its own `seedSql`
- [ ] `seedSql` contains data statements only, no DDL
- [ ] At least one testcase is `visible`, and at least two are hidden
- [ ] Hidden testcases cover empty result, single row, ties, `NULL`, rounding boundary, and constraint limits
- [ ] Visible testcase rows match the description examples exactly, value for value

Description:
- [ ] Sections in order: Description → Table Schema → Output Format → Examples → Constraints / Rules → Note
- [ ] Every table and column is documented and matches `schemaSql`
- [ ] One example per visible testcase, each with Input, Expected Output, and a per-row Explanation
- [ ] Ordering, rounding, `NULL`, tie-break, and empty-result rules are all stated
- [ ] Note states the tables are already created and that DDL / DML must not be written
